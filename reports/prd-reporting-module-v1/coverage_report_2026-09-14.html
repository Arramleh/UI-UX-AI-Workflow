1. Executive summary

Read the per-screen numbers, not the headline. The overall 74.2% is an average across two very different kinds of surface. The four interactive screens — the actual application — score between 83% and 100%, because the Sand library already owns the list pattern, the form families and the scope vocabulary this module needs. The three rendered artifacts — the produced PDF, the Excel workbook and the delivery email — score between 7% and 50%, because the library contains no document, spreadsheet or email surface at all.

That second number is not a weak design system. It is a surface-kind mismatch: an application-UI library measured against print and email output. Treating it as a coverage hole would commission eleven application components that solve nothing. The decision it actually raises is ESC-1, below.

ESC-1 — escalated product decision, unanswered

Are the produced PDF, the Excel workbook and the delivery email design-system surfaces that Sand builds and owns as Figma components — or are they renderer templates specified as a data-and-layout contract in developer handoff, outside the design system?

Why no component choice fixes it: No choice of component resolves it. The Sand Design System Library is an application-UI library: a full-file census across every node name and every text string, over all 14 pages and all 85 component sets, returns ZERO document, spreadsheet or email surfaces. This is not one missing component but the absence of a whole surface kind, and the answer decides what gets built rather than which component is used. It also decides whether the design system takes on print and email-safe layout, which have different constraints from everything in it today — email in particular cannot use the spacing-token model the library documents as mandatory, because transactional email is table-based and inline-styled with no CSS variables.

  1. Build a shared "Report Document" component family in Figma (page frame, header block, section block, empty block, placeholder block) plus a transactional-email family, and treat Excel as a data contract only. Covers 12 of the 13 no-match requirements with reusable parts; adds print and email layout to the design system’s remit.
  2. Treat all three surfaces as renderer templates: specify them in /developer-handoff as content and data contracts (section order, unit scaling per REQ-59, sheet naming, no-readings copy, placeholder copy) and build no Figma components for them. Fastest, and honest about Excel; but the PRD is explicit that the PDF and email are "designed surfaces in their own right, not a default wrapper", so this reads as overriding the PRD and needs to be an explicit decision rather than a default.
  3. Split by surface: build the PDF and email families in Figma because the PRD calls them design surfaces, and treat Excel as a pure data contract because a workbook has no visual surface a person navigates.

Recommended: Split by surface (option 3). It follows the PRD where the PRD is explicit and stops short of pretending a spreadsheet is a design artefact. Scope both new families as shared rather than module-specific, per the system-wide-reuse rule — any future exported document or transactional email needs the same parts.

Blocks: REQ-57, REQ-60, REQ-61, REQ-62, REQ-63, REQ-64, REQ-65, REQ-66, REQ-67, REQ-68, REQ-69 across Generated PDF Document, Generated Excel Workbook, Delivery Email.

Nothing is holding the work open. Gate 2 reviews built components and seeds no decisions, so nothing in the pipeline will hold the work open while this is unanswered. It must be raised out loud, in the gate 2 packet, or it will surface only in the closure report — after the module is built.

5. Library defects this feature surfaced

These are faults in the shared design system, not gaps in this feature. Both should be fixed in the shared components, where every other feature gains from them.

FIND-1 — high

affects REQ-38

The Button component set documents a Loading state that does not exist. Its handoff frame on the Buttons page states "Default, Hover, Loading, Disabled" and "Loading exists for both Default and Error — the icon slot is replaced with a spinner (Icons/General/Loading)". Enumerating all 108 children of the set (node 88:3690) gives State = Default | Hover | Disabled only, in every Semantic, Type and Size.

Why it matters: A direct match asserted from that documentation would be wrong, and the error would surface only during assembly. REQ-38 (generate once, on demand) needs it.

Fix: Add the documented Loading state to the shared Button set.

FIND-2 — high

affects REQ-75

No focus state on the non-field controls. Button (108 variants), Checkbox, Radio Button, Switch, Flat Tab and Button Tab expose no Focused value, while all eight field families (Input Field, Text Area, Search Field, Date Picker Field, Phone Number Input, Autocomplete, Tags Input, Number Input / Stepper) do carry State=Focused.

Why it matters: WCAG 2.2 AA (REQ-75, decided at gate 1) requires a visible focus indicator on every interactive control. The library has a focus idiom already, so this is an omission rather than a convention — which makes it cheap to close and serious to leave.

Fix: Add Focused to Button and the four control families, matching the field families’ treatment.

FIND-3 — medium

affects all

The Figma Variables API is unreadable with the available credentials (/v1/files/:key/variables/local returns 403 — the token lacks file_variables:read, and the plan is starter tier). Colour and spacing tokens were read from the library’s own documented Colors and Spacing & Effects pages instead.

Why it matters: Token bindings can be checked by NAME but not verified by variable ID. Gate 2’s tokens_and_variables_bound check therefore rests on visual inspection rather than on a machine-readable binding.

Fix: Grant file_variables:read, or accept name-level verification at gate 2 and say so in the signoff note.

FIND-4 — critical

affects all

The Figma MCP server refuses this file: the account (moanes@sandbase.com) holds a View seat on a starter-tier plan, and get_metadata, get_libraries and use_figma all return "you don’t have edit access to this file". REST reads work, which is why every analysis stage in phase 2 completed.

Why it matters: The component pass (/figma-component-pass) and page assembly (/figma:figma-use) write through the Plugin API via MCP. Both are blocked until the account is granted edit access. This blocks the run before gate 2.

Fix: Grant the account edit access to the Sand Design System Library, or run the build passes from an account that has it.

7. Implementation roadmap

Phase 1 — Answer ESC-1 before anything is built

0 component(s) · effort low · 1 decision, blocking

The design system contains no document, spreadsheet or email surface of any kind. No gate holds this open, so it must be answered deliberately. Until it is, phase 4 below cannot be scoped and the three rendered-artifact screens cannot be assembled.

Phase 2 — Fix the two library defects this feature surfaced

9. How this was measured

The library walk. The Sand Design System Library was read live through the Figma REST API as a full, depth-unlimited file tree, and the walk descended into every one of its 85 component sets: 268 standalone components and 710 nested variants, 1063 component nodes in total across 14 pages.

No gap here rests on a keyword search. Every no-match was established by a census across every node name and every text string in the whole file, after that descent — the walk that finds a component nested inside a set rather than promoted to the top level.

Known limits. Figma Variables API (/v1/files/:key/variables/local) returned 403: the token lacks the file_variables:read scope and the plan is starter tier. Colour and spacing tokens were therefore read from the library’s own documented Colors and Spacing & Effects pages, which state the hexes, token names and CSS variables explicitly. Consequence: variable IDs are NOT recorded, so downstream a token binding can be checked by NAME but not verified by ID. The MCP server (get_metadata / get_libraries / use_figma) is unavailable on this account. Read stages can use REST; the phase-2 component pass and phase-3 assembly need the Plugin API through MCP and will be blocked until the account is granted edit access.
